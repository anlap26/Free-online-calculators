JSON, CSV and SQL formatter

JSON is parsed and printed with an indent. CSV keeps quoted commas inside the cell. SQL is broken before a short list of words and is not a full parser.

JSON is parsed, then printed

JSON goes through JSON.parse and then JSON.stringify with the indent you set. The indent is a small whole number of spaces. If the number is out of the range the script accepts, it falls back to two spaces. The keys come out in the order the parser produced, which for ordinary objects is the order they had in the text. The formatter does not sort keys to make two files look alike, and it does not drop a key you did not mention.

If the text is not JSON, the error message is the engine's own parse error. The page does not rewrite that message into a friendlier guess. A trailing comma, a single-quoted string, or a comment is invalid JSON, and the engine will say so in its own words. Fix the text and run it again. The script will not silently strip comments.

CSV keeps a quoted comma in one cell

The CSV reader walks the text. A comma outside quotes starts a new cell. A newline outside quotes starts a new row. A quote starts a quoted cell, and a doubled quote inside that cell is one quote character, not the end of the cell. A row written as Doe, Ann inside quotes stays one cell, even though a comma sits between Doe and Ann. A bare comma without quotes is a real separator. A row that never closes its quote is an error, not a guess. The printer then quotes a cell again only when the cell contains a comma, a quote, or a line break.

SQL is a pretty-printer, not a parser

The SQL step checks that quotes and parentheses balance, then breaks the line before a fixed list of words and uppercases those words. The breaks include SELECT, FROM, WHERE, AND, OR, JOIN, GROUP BY, and ORDER BY, along with a few neighbours such as HAVING, LIMIT, and INSERT INTO. Words inside a quoted string are left alone, because the balance check tracks the quote. A line comment that starts with two hyphens is skipped while the parentheses are counted.

This is not a full SQL parser. It will not catch a wrong column, a missing table, or a dialect feature it has never heard of. Balanced quotes and balanced parentheses are the only structural checks. A statement can be neatly broken and still be wrong when it runs. Do not treat a successful format as permission to execute the statement against production data.

Pretty-printing is also not hosting. Cloudways is a host you might use when a query has to run somewhere.   • A quoted comma stays inside one CSV cell. A doubled quote is one quote.
  • SQL is uppercased and broken on a short word list. A bad column still passes.

Questions people ask

What does a JSON error look like?

It is the engine's own parse error from JSON.parse. The page does not replace it with a guess.

Does a comma inside quotes split a CSV cell?

No. A field such as Doe, Ann kept inside quotes stays one cell. A doubled quote inside the field is a single quote character.

Will the SQL formatter catch a wrong column?

No. It checks that quotes and parentheses balance, then breaks and uppercases a list of words. It is not a full parser.

Which SQL words start a new line?

The printer breaks before SELECT, FROM, WHERE, AND, OR, JOIN, GROUP BY, and ORDER BY, and before a few neighbours such as HAVING and LIMIT.

Is the text uploaded or run?

Neither. Formatting happens in the browser. A database does not see the statement.
